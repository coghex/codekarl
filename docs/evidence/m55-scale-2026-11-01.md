### K3 and the texture-bytes budget (a departure from CK-130, stated)

CK-130 ran K3 with `texture_bytes` = 64 MiB. On Vulkan that is exactly **one block of the image pool** (`crates/gpu-vulkan/src/memory.rs`, `BLOCK_SIZE` 64 MiB): `texture_bytes` is reserved in whole blocks (or dedicated allocations at their queried size), and the checker, uploaded when the presenter starts, holds a range of the first block for the presenter's whole life. At 64 MiB every K3 image (16 MiB, MoltenVK prefers dedicated memory at 4 MiB and up) is therefore refused, whatever K1 and K2 did — scale run 2's first `caps` showed exactly that (8 of 8 refused, `67108864 of 67108864 reserved`). The caps worker now runs at 128 MiB (the first block + room for four 16 MiB images), K3's verdict unchanged. `caps-min` (a fresh presenter at 64 MiB, one 16 MiB request before anything else): **refused with `(67108864 of 67108864 reserved)`, 0 ready**: the reservation exists at start-up with no K1/K2 history. This does not exclude a range left behind in the old caps process (a checker-only block and a checker-plus-leak block reserve the same total), and reserved bytes returning to one block after K3 are not shown (no counter exists for the level; none was added). **Product note:** the same `texture_bytes` number has a different capacity on Vulkan than on Metal; at the minimum only images that suballocate into the checker's block can load. The manager raised this with the owner.

## Is anything really wrong? (for the owner)

**Yes, one thing, and it is not a correctness failure.** On glfw-vulkan/MoltenVK the 65,536-quad / 32,768-distinct-texture scene (one draw call) takes **about 150-155 ms of GPU time per frame (about 6 frames a second)** against **0.625 ms (p95) on Metal**, roughly 250 times as much, in both the Rust harness (static-bindless: 152.5 / 157.5 ms) and the application's Lua path (155 / 157.5 ms), which agree to within a few percent; the per-revision mode (49,152 draw calls) is the same (162.5 / 167.5 ms). What is drawn is right (verify decoded all 32,768 identities; 0 validation messages), and a smaller scene is fine (heterogeneous: GPU p95 0.3 ms at 60 Hz). Churn is slower by the same kind of factor: GPU p95 57.5 ms against 0.65 ms (88.5x), and with validation on 45 ms against 0.8 ms (56x); the loads run at about half of Metal's rate. The heterogeneous scene matches Metal (GPU p95 0.3 against 0.35 ms) and, notably, the per-revision static job is as slow as the bindless one (167.5 against 157.5 ms p95) while Metal's per-revision job is not (2.475 ms): which suggests (not tested) that the cost follows the scene with 32,768 live textures rather than the bindless table alone. The cause has not been investigated; untested candidates: MoltenVK's handling of a 131,072-slot bindless table with 32,768 bound images per encoder (residency/argument buffers), or timestamp attribution. The §11.3 timing numbers are not met on this backend; per the owner's rule they are reported, not gated. Proposed as a follow-up issue, not something CK-162 fixes.

Smaller findings: the Vulkan texture-bytes budget is block-granular (above); in this run K2 did not observe a texture still waiting (all 65 reloads were shown before the first poll, within a frame of the requests; Metal's run saw all 65 waiting at its first poll); this run cannot establish that a waiting texture can never be seen on this backend and recipe. K2 therefore claims "no frame across the transition shows a wrong image" rather than "a waiting texture showed its old image"; the Rust phases report presenter metrics plus scene cadence while both-owner/common-window/delivered/missed readings come from M-lua (manager ruling, CK-162 review 1).
