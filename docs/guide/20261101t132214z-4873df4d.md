## Findings

### GUIDE-1. Wait for the Vulkan first-frame report before asserting it

**Disposition:** repair proposal. **Suggested priority:** P2. **Verification:** source-verified; no reproduction or probe run.

**Contract:** CK-157's first-frame test promises that a scene pending at start draws the checker and reports `FirstFrameQueued` once. `vision.runtime-first` calls for an observable, reliable lifecycle; this is a test-observation defect, not evidence that a production report is lost.

**Evidence at the pin:**

- `crates/gpu-vulkan/src/render/scene.rs:1184`, `Core::drawn`: it increments `scene_stats.frames` under the stats mutex and drops that guard at line 1191. It subsequently writes the drawn record, publishes the generation, updates test hooks and only then enqueues `FirstFrameQueued` at line 1217.
- `crates/gpu-vulkan/tests/window_scene/mod.rs:412`, `the_first_frame_shows_the_checker_for_a_pending_key`: line 416 waits only for `stats.frames >= 1`; line 430 immediately requires `reports(&presenter) == [FirstFrameQueued]`.
- Its `wait_stats` helper at line 304 delegates to `Rig::wait` (`tests/window.rs:244`), which returns as soon as that predicate is true. `reports` (`tests/window.rs:378`) drains only currently queued reports. Neither helper waits for the later report publication.

**Reachable consequence:** the render thread can be descheduled after releasing the stats mutex and before enqueuing the report. The test thread can then satisfy the frame predicate, inspect the already-built checker frame and drain an empty report queue. A correct presenter fails the test. Sleeping during unsuccessful polls does not order the later report after a successful poll. No failure rate is claimed.

**Deduplication:** CK-160 repaired Metal's analogous ordering and explicitly left a Vulkan repair to a separate issue. Its result noted the pattern but filed no issue. Authenticated manager answer `8uue29m7bdjne72fueqgbvbqwi` confirms this is neither tracked nor owner-deferred and requests this draft for the owner walk. CK-167 fixes a different Metal snapshot race. CK-135/140/146 remain unrelated parked Cocoa tests.

**Smallest action recommended:** make this test wait for the report it asserts, using the existing bounded event-pumping mechanism and retaining every observed report. Preserve exactly-once and no-failure assertions and all checker/proof checks. A production publication-order change is an alternative only if its observation contract and lock ordering are explicitly specified; do not move the report ahead of drawn-generation publication.

**Exact issue draft for approval and manager filing:**

> **Title:** Vulkan first-frame checker test waits for the report it asserts
>
> **Problem:** At the reviewed pin, `Core::drawn` publishes `SceneStats.frames` before enqueuing `FirstFrameQueued`. `the_first_frame_shows_the_checker_for_a_pending_key` waits for the frame count and immediately drains reports, so a render-thread deschedule between those publications causes a false failure. See the pinned file/line evidence above. CK-160 explicitly excluded a Vulkan repair; no existing issue covers this case.
>
> **Required behavior:** The test completes its first-frame assertion only after observing the report itself. Use the existing bounded wait/pump facility. Preserve all drained reports across polls, fail on an unexpected `Failed`, require one first-frame report, and retain the checker counters, previous-proof and proven-end assertions. Check the final report collection for duplicates as well. A missing report must still fail at the existing bound. Do not add a fixed delay, automatic retry, wider timeout, new engine counter or weaken the lifecycle assertion.
>
> **Coverage:** Add focused coverage of the observation helper/protocol using supplied report states: frame observed but no report yet remains pending; later one report succeeds; a failure or duplicate fails; no report never becomes success. Keep the real first-frame window case. The worker/reviewers run the normal planned check in a manager-granted slot; batch CI remains the acceptance evidence. Codex writes and runs no crash/panic/fault probes under the standing owner restriction.
>
> **Scope:** Vulkan window-test observation/helper code and its focused tests. No shader, renderer policy, resource lifetime, metrics or Metal change. If production ordering must change instead, return that contract choice to the manager before implementation.

**Owner question for the manager's walk:** “File and fix this bounded test-observation repair?” Recommendation: yes. The draft remains unprocessed until the owner decides and the approved disposition is carried out.
