## Findings

### [#94] GUIDE-1. Make defensive Metal refusal consumption once-only under concurrency

**Disposition:** repair. **Priority:** P3. **Verification:** verified legal interleaving, independently reproduced with a scheduling seam.
**Principle:** `vision.logging`; CK-92 r3's single-delivery defensive-refusal contract.

**Evidence:** [metal.rs](../../crates/render-2d/src/metal.rs), lines 62–74. `take` removes the first message and releases its temporary
mutex guard at line 71, then sets `reported` at line 73. A producer can acquire the mutex between those operations, see no message and
`reported == false`, and store a second message. A subsequent `take` returns that message too.

The guide extracted the pinned `Refusals` implementation verbatim into a standalone harness. A 200,000-round natural stress run did
**not** reproduce the race. A second harness added only a scheduling gate after removal and before the flag store; the producer then
records in that legal interval. It returned `Some("first")`, then `Some("second")`. The source, seam diff and logs are retained under
`.pipeline/coordination/guide/20261022t135100z-bcf77413/` as `refusals-race.rs`, `refusals-race.log`, `refusals-forced.rs`,
`refusals-probe-seam.patch` and `refusals-forced.log`. No tracked production source was changed.

**Consequence:** one extra failure report on an already-failing defensive conversion path. The first failure remains visible, the
single main-thread consumer drains finitely, and cleanup proof is unaffected. Ordinary bridge placement prevents the invalid geometry
that reaches this defence; public supplied snapshots and forced-refusal tests can exercise it. This does not demonstrate a normal-rendering
failure or establish a natural race frequency.

**Deduplication:** this is the existing, unfiled CK-92 review-2 F5, independently checked, not a newly discovered defect. No open issue
at the pin covers it. The cursor had no open finding. CK-93's coverage recommendation below is a different concern.

**Action:** serialize consuming the message and marking it reported; keep the first reason and add a deterministic test against the
actual latch. The repair is small enough to do before 4.5, but it is not an architectural prerequisite.

**Original proposed issue draft — retained for provenance; filed and repaired as CK-94:**

> **Title:** Make Metal conversion-refusal reporting once-only under concurrency
>
> **Type/priority:** bug, P3. **Depends on:** CK-92 (accepted).
>
> **Problem:** `Refusals::take` releases the message mutex before setting `reported`. A concurrent producer can insert a second reason
> in that interval, so an already-failing run receives two failure reports despite the once-per-run contract.
>
> **Required behavior:** consumption of the first reason and the reported-state transition form one synchronized operation relative to
> `record`. Keep the first reason, return it once, and reject later reasons. Preserve the existing wake, failure and teardown behavior.
>
> **Acceptance:** a deterministic concurrent-record regression exercises the actual latch at the consumption boundary and fails on the
> accepted implementation; the repaired implementation reports exactly once. Existing serial and idle/pre-wait refusal tests pass.
> Run the planned check; the normal batch supplies full validation.
>
> **Scope:** `crates/render-2d/src/metal.rs` and its focused tests. No renderer/API redesign or GPU lifecycle change. Evidence:
> `docs/guide/20261022t135100z-bcf77413.md`, GUIDE-1, and its retained scheduling probe. Route through ck-manager and normal independent gates.
