## Findings

### [#73] GUIDE-1. Preserve presenter failures through completed teardown

**Disposition:** repair. **Priority:** medium, before extending the shared loop for 3.5. **Verification:** reproduced.

**Contract:** CK-64 r4 §2.6 requires a failed command-buffer completion to report `Failed`, even when completion proves resources unused. CK-65 r5 §3.4 and `apps/codekarl/src/main.rs:31` require failure status 1 unless incomplete status 3 wins. This supports `vision.logging` and `vision.runtime-first`.

**Evidence:** `crates/gpu-metal/src/presenter.rs:991` polls completion errors during teardown, queues a failure, and can still return `CleanupResult::Proven`. `crates/window/src/main_loop.rs:428` only polls cleanup once it leaves the run loop; it never takes another presenter report. It returns the original `Closed` or `Quit`. `apps/codekarl/src/windowed.rs:153` maps those to successful runtime ends. A close or quit can also bypass a failure already queued before teardown (`main_loop.rs:296`).

The test-only probe queues `Failed` from the presenter's stop request and returns `Proven`. It runs the real executable control path, Lua owners, logger, teardown, both shutdowns and final status. The result is **exit 0 with no error record**; the assertion requiring exit 1 fails. The native presenter's existing `completion_error_never_lost` cases (c/d), `crates/gpu-metal/tests/presenter.rs:935`, already demonstrate that a real presenter reports an error while returning `Proven`. The probe does not claim a spontaneous hardware fault.

**Consequence:** a failed GPU operation can be reported as a clean close, or retain only the signal status. Resource cleanup remains proven; rendering success does not.

**Smallest action:** make terminal presenter failures observable through shutdown and fold them into the loop/application result without extending teardown deadlines. Preserve existing primary diagnostics and incomplete precedence. This is distinct from CK-64's repaired token-error loss and CK-65's repaired late Lua traceback loss.

**Exact approved proposal — owner approved 2026-10-20; filed as CK-73**

> File and route to ck-manager a repair titled **“Preserve late presenter failures through window teardown.”**
>
> A presenter may report `Failed` during shutdown and still prove its resources released. Today `ck-window` stops reading reports when close/quit begins, so the application can exit 0 without reporting the error.
>
> Define and implement bounded terminal failure observation across the presenter/window boundary. A failure reported before the presenter is observed finished must remain visible: after otherwise clean close or signal quit, emit its diagnostic once and exit 1; incomplete cleanup still exits 3 and retains resources. Preserve an existing primary failure and report any distinct late presenter failure once. Keep current teardown deadlines and normal shutdown order.
>
> Add deterministic tests for failure queued before close/quit, failure arriving during teardown with `Proven`, coexistence with an earlier failure, and `Unproven` precedence. Include an executable-boundary test using real runtime/Lua/logging/status and a scripted presenter; retain the existing native completion-error tests. Clarify the owning trait/loop contract. Use the normal fresh spec review, submission review and batch gates.

### [#74] GUIDE-2. Fail native test supervision when diagnostic reads fail

**Disposition:** repair. **Priority:** medium. **Verification:** reproduced by injected read failure in both supervisors.

**Contract:** CK-63 r5 and CK-64 r4 require native validation/checker tests that fail rather than silently pass without valid evidence. Their test module documentation promises failure on checker/validation diagnostics. This supports `vision.logging`; it is also a concrete consequence of duplicated supervision.

**Evidence:** `crates/window-cocoa/tests/window_cocoa.rs:974` and `crates/gpu-metal/tests/presenter.rs:1365` discard `read_to_end` errors and send the partial buffer as a successful string. The callers then judge status 0 plus an empty/truncated stderr as clean. In each probe, an injected `Read` error yields empty stderr and the existing `judge` returns `Ok(())`. No production code or judgment function was changed.

**Consequence:** a failed diagnostic read can yield false green validation; the helper path can also treat truncated process-list output as a complete listing. This is a verified error-handling gap, not a claim that the passing full run suffered an I/O error. It does not bypass a checker-induced nonzero process exit.

**Smallest action:** propagate reader errors to both worker and helper callers, fail the case on incomplete inspection, and test an error before any bytes and after a partial prefix. Keep bounded cleanup. The application supervisor already reports these errors (`apps/codekarl/tests/supervisor/mod.rs:126`); CK-65's repair was not carried into these separate implementations. Broad supervisor consolidation is optional and is not required by this finding.

**Exact approved proposal — GUIDE-2, owner approved 2026-10-20; filed as CK-74**

> File and route to ck-manager a bug titled **“Fail native test supervision on diagnostic read errors.”**
>
> In both `crates/window-cocoa/tests/window_cocoa.rs` and `crates/gpu-metal/tests/presenter.rs`, reader threads discard `read_to_end` failures. Worker validation can therefore pass on incomplete diagnostics; helper output can be mistaken for a complete process listing.
>
> Propagate read failure to every worker and helper caller. A failed read must fail the case even if the child exits zero, stderr is empty, or the bytes read so far appear clean. Partial helper output must never establish that the process group is empty. Preserve the existing bounded wait, kill/reap and pipe-cleanup behavior and expose the read failure in the reported error.
>
> Add deterministic coverage in both supervisors for errors before any bytes and after a partial prefix, exercising worker judgment and helper-output handling. Retain the existing native checker/validation cases and require the full check, including Metal. Keep the change confined to these test supervisors and their regression tests; shared-supervisor consolidation is not required. Use fresh independent spec and submission review and normal batch publication.

### [no-issue] GUIDE-3. Describe `on_opened` as queued presentation, not visible pixels

**Disposition:** documentation drift. **Priority:** low. **Verification:** source/contract comparison.

**Evidence:** `README.md:117` says `window.on_opened(fn)` runs once the window is “on screen.” The public contract at `crates/window/src/link.rs:82` says the first frame is queued for presentation and explicitly says this is not proof it is visible. The loop posts `Opened` from that report; no display confirmation exists. CK-64's token observations also distinguish release/completion from actual display.

**Consequence:** the Lua API documentation promises a display guarantee the application cannot provide.

**Applied disposition:** the owner approved this correction on 2026-10-20. README now says “runs once the first frame has been queued for presentation; this does not prove it is visible.” The correction and this disposition are published together through the ordinary docs lane. Rechecked against `PresenterReport::FirstFrameQueued`; no runtime change or issue is needed.
