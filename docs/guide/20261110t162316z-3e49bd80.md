### [#251] GUIDE-1. Partial staffing fills the first method instead of sharing proportionally

**Priority / disposition:** P2, repair; manager filed CK-251, effective r2 observed during the follow-up.
**Verification:** verified from source and the signed formula.
**Principle / contract:** `vision.economy-first`; [economy-design.md](../economy-design.md) §3.4, “Staffing per method (r14, exact)”, forbids integer `staffed_m` and shares building staffing inside each output numerator. CK-227 requires exact staffing per method.

**Evidence:** `crates/economy/src/lib.rs:5048` initializes `remaining_workers`; lines 5105–5106 assign and subtract an integer `method_staffed` in method order. Lines 5149–5168 use that allocation and the method's positions in the output fraction. With one farming level, one fishing level, 20 paid positions and 10 workers, farming receives all 10 and fishing receives none. The signed rule produces half of each method's fully staffed output. Deaths and movement make partial staffing reachable; this changes food supply and pay, not merely presentation.

**Deduplication:** CK-227 review N3 noticed the reading but was not an owner-approved deviation, deferral or tracked issue (manager answer `gukar9pkjqf6n2wmghxmrnr8dw`). CK-251 now explicitly repairs it; spec r2 digest `0779ef0bb1b9030ae7232f44e2076f6ce5c92533ba6bc6fcee5006cbd8c0b3f7`.

**Applied disposition:** route the repair through CK-251. Use building-wide staffed/positions with the existing summed method suitability, fertility, coverage and season factors; preserve per-good exact carries. Its spec includes half-staffed and uneven-level literal outputs/carries, full staffing, one method, coverage, unchanged herds and save continuation. No new guide issue or implementation is needed.

### GUIDE-3. Expected yield ignores the fertility factor used by farm production

**Priority / disposition:** P3, owner decision.
**Verification:** the differing calculations are verified; the intended meaning after fertility is unresolved, so this is not classified as a settled contract violation.
**Principle / contract:** `vision.player-information`; economy design §3.22 defines expected annual food at land suitability and full staffing/coverage, plus dairy. Later §3.24 makes fertility affect farm yield as well as land room.

**Evidence:** `apps/codekarl/src/game/view.rs:301`–`:353` computes method annual output from suitability alone, plus cattle dairy. `:496` calls it without land quality. Actual farm production at `crates/economy/src/lib.rs:5142`–`:5165` applies quality/reference to non-sea methods. Two otherwise identical places with different quality can show identical expected yield while producing different farm food. Full staffing does not explain that difference.

**Deduplication:** manager answer `t8c9zqkwqwe8utw7bq5cgzy3aw` confirms no issue or ruling. The CK-231 F3 owner ruling concerned herds only; CK-233 names production and the starting estimate, but not this map mode.

**Exact pending owner question:** “Should expected yield include the place's fertility at full staffing and coverage? I recommend yes: scale only non-sea method food by the same quality/reference ratio as farm production, leaving fishing and dairy unchanged. Alternatively, keep the current number as fertility-normalized potential and label/document it that way. Which meaning do you want?”

**Repair draft if the recommended meaning is chosen:** make the view's full-staff annual food projection take the same land quality/reference ratio as production, retain current suitability and dairy rules, and keep deterministic integer rounding. Add windowless literal comparisons for reference quality, lower/higher quality, mixed farming/fishing, and dairy; prove the value reaches the yield-mode input. No new GPU algorithm, actual-staff projection or production change. Ask the manager to file the approved meaning and coverage, then mark this finding only after that disposition exists.

### GUIDE-4. Displayed storage capacity counts owners whom goods receipt excludes

**Priority / disposition:** P3, owner decision followed by repair.
**Verification:** the disagreement is verified; which capacity is right remains an owner choice.
**Principle / contract:** `vision.player-information`; economy design §§3.14–3.15 use capacity per employee, while §3.4 counts owners as employed. CK-227 review N5 left the interpretation unresolved.

**Evidence:** `apps/codekarl/src/game/view.rs:379`–`:390` counts owners plus paid workers as employees; `:420` passes that to `building_capacity_ml` at `:289`. The receipt path's `worker_count` at `crates/economy/src/lib.rs:2950` counts paid workers only, and `store_capacity_ml` at `:2962` uses it. A holdings with 10 paid workers and 2 owners therefore displays 14,040 L while receipt admits only 11,700 L. The discrepancy feeds the place total and stockpile map denominator as well as the building panel: overflow can occur while the UI still shows room.

**Deduplication:** manager answer `t8c9zqkwqwe8utw7bq5cgzy3aw` confirms no settled owner ruling; designer-1 is already taking CK-227 N5 to the owner. This finding adds the concrete view/receipt mismatch; do not create a second competing owner question.

**Exact pending owner question:** “For a farm or holdings, do owners earn the same storage allowance as paid workers? I recommend counting both, consistent with owners being employed. Whichever rule you choose, should receipt, the building/location panel and stockpile map use one capacity calculation?”

**Repair draft after that answer:** expose the agreed capacity rule from the economy crate and use it for receipt and view construction. Remove the independently reimplemented owner count from the projection. Cover owners plus workers, owners alone, no employees, unchanged level-based storehouse capacity and a literal receipt boundary equal to the displayed capacity; keep map-mode normalization unchanged. If the owner chooses paid workers only, correct the view and clarify “employee” in the contract. Do not infer that choice from currently accepted code.

### [#252] GUIDE-5. Field room subtracts sea methods as if they occupied farmland

**Priority / disposition:** P3, repair; manager filed CK-252, depending on CK-250 because they edit the same view.
**Verification:** verified from source and the explicit land rule.
**Principle / contract:** `vision.player-information`; economy design §3.24 says “fishing and coastal levels need sea, not fields”.

**Evidence:** `apps/codekarl/src/game/view.rs:524`–`:553` subtracts `land_per_level × building.levels` for farms/holdings, including fishing. The economy's method assignment charges land only for methods whose resource is not sea. With ten field units, land cost two, one farming level and one fishing level, the view says six free where the rule leaves eight. The value is exposed through the game view/API, although the shipped location panel does not currently display it; severity is proportionate to that narrower exposure.

**Deduplication / applied disposition:** CK-233 review N1 was an unfiled non-blocking note, neither tracked nor deferred. Manager answer `d46v74fcsr2p4ag5dmp5eanwfe` filed CK-252, spec digest `abf1120894b3ac340998184663c7baf08a776d160bbac4aeb25aa6a2629b52a1`. Count non-sea method levels using the definition's land requirement rather than a hard-coded building-id match. Add a literal mixed farming/fishing view test; no change to the correct load-time assignment rule.
