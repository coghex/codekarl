## Findings

### [#100] GUIDE-1. Make captured surface pixels visible to the host

**Disposition:** repair. **Suggested priority:** P2. **Verification:** verified missing synchronization by source and API contract;
stale or incorrect bytes have not been reproduced. No fault probe is needed to establish the missing dependency.
**Principle/contract:** `vision.small-libraries`; CK-97 r2's observable surface-pixel acceptance and Vulkan host memory access rules.

**Evidence at the pin:** [capture.rs](../../crates/gpu-vulkan/src/capture.rs), lines 158–204, copies the swap-chain image into a
host-visible/coherent buffer, restores the image's presentation layout, and later maps/reads the buffer. Its final barrier concerns
only the image, with `TRANSFER_READ` and an empty destination access mask; neither barrier makes the buffer's transfer writes
available to host reads. [gpu.rs](../../crates/gpu-vulkan/src/gpu.rs), lines 689–695, ends the command buffer immediately afterwards.
[render.rs](../../crates/gpu-vulkan/src/render.rs), lines 440–457, observes the submit fence before
[render/quad.rs](../../crates/gpu-vulkan/src/render/quad.rs), lines 158–171, collects the capture; no intervening host dependency exists.

The [Vulkan fence-wait specification](https://docs.vulkan.org/spec/latest/chapters/synchronization.html#synchronization-fences-waiting)
distinguishes completion from host visibility: a fence alone does not provide the latter. The
[Khronos CPU-readback example](https://docs.vulkan.org/guide/latest/synchronization_examples.html#_cpu_read_back_of_data_written_by_a_compute_shader)
uses a host-read barrier before submission; coherent memory removes the invalidation step, not that barrier.
The project's offscreen path already has the corresponding transfer-write → host-read buffer barrier in
[readback_quad.rs](../../crates/gpu-vulkan/src/readback_quad.rs), lines 731–751.

**Consequence:** tests can read bytes whose visibility Vulkan does not guarantee, making the surface-pixel assertions unreliable
across implementations. Current passing captures and the owner's successful demo are real observations, but do not supply the
missing dependency. This path is requested through `TestHooks::capture_frames`; ordinary app rendering does not enable it.

**Deduplication:** no open issue at the pin; CK-97's accepted fix addresses partial cleanup/retirement, not host visibility.
No matching concern was found in the reviewed M4.5 Markdown reviews or the cursor's findings.

**Action:** add the buffer dependency after the copy and before command completion; preserve the image transition and the existing
fence-before-read ordering. Keep the repair in the Vulkan crate and validate the emitted dependency as well as actual pixel capture.

### [#101] GUIDE-2. Decide whether to harden the remaining Metal/Lua panic-payload boundaries

**Disposition:** owner decision. **Verification:** partially verified; implicit payload disposal is visible in source, but exact
runtime consequences at these boundaries are unconfirmed. This is a pre-existing risk, not a new M4.5 regression.
**Principle/contract:** `vision.runtime-first`; the stated caught-panic/reporting/cleanup guarantees at those boundaries.

**Evidence at the pin:** [gpu-metal presenter.rs](../../crates/gpu-metal/src/presenter.rs), lines 263, 900 and 936–944, implicitly
drop caught wake/join/render payloads. In particular, disposal in `unwrap_or_else` can unwind before the cleanup result is stored.
[lua runner.rs](../../crates/lua/src/runner.rs), lines 107, 166 and 179–185, similarly discards wake/flush/thread payloads;
[extension.rs](../../crates/lua/src/extension.rs), lines 261–270, records the host panic then implicitly disposes of its payload.
[owner.rs](../../crates/lua/src/owner.rs), lines 495 and 647, discards failed-join payloads. These differ from CK-96's explicit
Vulkan disposal helper, which catches a payload destructor's panic and forgets the secondary payload.

**Consequence/risk:** a supplied Rust callback can panic with a payload whose destructor panics. Dropping it can start another unwind
outside the intended catch, potentially interrupting reporting or cleanup; exact outcomes depend on the call stack and remain
unconfirmed here. The ordinary demo is not evidence of this unusual callback behavior. The worker's CK-96 tests/negative controls
support the mechanism in Vulkan, not a claim that equivalent Metal/Lua cases have run.

**Scope correction:** the brief also named the application's `boundary.rs`; [main.rs](../../apps/codekarl/src/main.rs), lines 62–63,
declares it only under `cfg(test)`. It is test scaffolding, not another production application boundary to repair.

**Deduplication/action:** CK-96 deliberately covers only Vulkan. No open issue covers the residual sites. Recommend separate focused
Metal and Lua follow-ups, retaining their existing outcome/retention contracts; do not make either depend on the other backend crate.
Confirmation would require worker-provided boundary-specific payload-disposal regressions and explicit negative controls, including
report delivery, cleanup classification and finished joins. Codex must not write or run its own fault probes until the owner lifts
the Daybreak restriction. This report does not authorize that work or claim those tests pass.
