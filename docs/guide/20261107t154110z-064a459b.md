## Findings

### [#CK-203] GUIDE-1. Preserve the default environment of textual Lua load

**Disposition:** repair. **Severity:** P2. **Verification:** source-verified; not executed.

**Principle/contract:** `vision.early-lua`, `vision.modding`; CK-196 required behaviour 2 restricts loading to text, while retaining ordinary textual loading.

**Evidence at the pin:** [deterministic.rs](../../crates/lua/src/deterministic.rs), lines 162–164, always calls `native.load(chunk, name, 't', env)`. Omitting the caller's fourth argument therefore becomes an explicit fourth argument containing nil. The locally vendored Lua 5.4.9 `lbaselib.c`, `luaB_load`/`load_aux`, distinguishes `lua_isnone(L, 4)` from nil and assigns an explicitly supplied environment to the first upvalue. [tests_profile.rs](../../crates/lua/src/tests_profile.rs), around line 373, tests a textual chunk returning the literal 42, which needs no environment lookup.

**Consequence:** `load("return math.abs(-1)")` can compile, but calling the resulting function cannot access `math`: its `_ENV` is nil. The same applies to expected profile globals such as `sim` or `config`. This is a normal supported usage, not binary loading or an environmental escape.

**Proposed repair draft:** Preserve whether the environment argument was supplied while still forcing text mode. When omitted, use Lua's ordinary global environment; when explicitly supplied, preserve the caller's value, including explicit nil. Add ordinary profile coverage for a text chunk reading a permitted global, an explicit environment table, explicit nil, and continued binary-chunk refusal. Do not broaden the gameplay profile's libraries or loader authority.

**Deduplication:** ck-manager confirmed no issue, review note or owner deferral in authenticated answer `tn2u8qn8fcdmpq4ydjcmpqnvww` (2026-11-07).

### [#CK-203] GUIDE-2. Make unsupported-key rejection independent of native table order

**Disposition:** repair. **Severity:** P3. **Verification:** source-verified; not executed.

**Principle/contract:** `vision.reproducible-saves`; CK-196's deterministic gameplay profile and CK-200's stable text behaviour.

**Evidence at the pin:** [deterministic.rs](../../crates/lua/src/deterministic.rs), lines 68–77, rejects the first unsupported key encountered by `native.next`, before sorting the supported keys at lines 80–85. Its diagnostic calls `stable_tostring(key)`, which can invoke the key's `__tostring`. Lua 5.4.9's native table implementation hashes collectable object keys by address and walks the resulting nodes in `luaH_next`. The unsupported-key tests in [tests_profile.rs](../../crates/lua/src/tests_profile.rs), lines 323–368, exercise individual invalid keys rather than competing invalid keys.

**Consequence:** With at least two unsupported table keys whose `__tostring` methods return different strings, allocation-dependent native traversal selects the error text and which metamethod runs. A caught error can consequently produce different script-visible output or side effects. Both executions reject the invalid table; ordinary supported-key iteration remains sorted. That narrow reach is why this is P3.

**Proposed repair draft:** Make validation and its diagnostic independent of native traversal order. Do not call the arbitrary first invalid key's metamethod to choose the error. Use a stable generic diagnostic or a deterministically selected classification; preserve integer-before-string ordering and explicit `__pairs` delegation. Add profile tests with multiple unsupported keys and custom `__tostring`, alongside the existing supported-key ordering tests.

**Deduplication:** ck-manager confirmed untracked and not deferred in answer `qg3ccc59mm6gn33cnthp8jihme` (2026-11-07), agreeing the severity should reflect that two invalid keys are needed and both cases already error.

### [#CK-204] GUIDE-3. Apply location overlays before terrain crop/jitter early returns

**Disposition:** repair. **Severity:** P3. **Verification:** source-verified; no render or preview run.

**Principle/contract:** `vision.modding`; CK-193 required behaviour 5 specifies river, then location, then terrain precedence, with CPU/GPU byte parity.

**Evidence at the pin:** [map/src/lib.rs](../../crates/map/src/lib.rs), lines 480–490, checks rivers first but returns sea for crop rejection before reaching the location lookup at lines 537–538. [scenario.rs](../../crates/map/src/scenario.rs), lines 1130–1165, clips prepared location pixels by their **unjittered** centres. A valid retained overlay pixel can therefore have its terrain sample jitter outside. The existing colour test at [tests.rs](../../crates/map/src/tests.rs), lines 507–510, already names a moved-outside terrain pixel `(0, 2)` at step 34. Both GPU passes draw location quads after terrain without that jitter rejection: [Vulkan gpu_map.rs](../../crates/gpu-vulkan/src/gpu_map.rs), lines 1396–1428, and [Metal presenter.m](../../crates/gpu-metal/native/presenter.m), lines 371–391.

**Consequence:** A marker/house/building pixel at a valid crop edge can disappear from `map-preview` and the CPU readback oracle while remaining visible in the application. This also weakens parity tests using that oracle.

**Shipped-data limit:** This does **not** affect the current Ireland-768 places. Static arithmetic over the 94 authored coordinates, the published Mercator projection and crop gives a minimum cell-centre margin of 47.5 cells (`nendrum`). At the enabled steps, even the maximum permitted glyph/house reach plus all jitter amplitudes is under 14 cells. This was a data calculation, not product execution or a historical-geography validation.

**Proposed repair draft:** Apply the prepared location overlay after rivers and before terrain sampling/early returns, preserving invalid-step handling and the preparation layer's crop clipping. Add a CPU reference regression for an inside-crop overlay whose jittered terrain sample leaves the crop, a river-over-location assertion, and a fixture parity case through the existing backend encoders under the normal repair workflow. No new map rule or shader redesign is needed.

**Deduplication:** ck-manager confirmed untracked and not deferred in answer `y9vnk5eqmzqxjvrtar2x6hysfn` (2026-11-07).

### [#CK-205] GUIDE-4. Retain Metal's overlay palette with its map input

**Disposition:** repair. **Severity:** P3. **Verification:** source-verified contract deviation; no cost measured.

**Principle/contract:** `vision.responsiveness`, `vision.small-libraries`; CK-193 required behaviour 4 says the palette lives in a small buffer uploaded with the map input, following the existing render-owner lifetime rules.

**Evidence at the pin:** [Metal presenter.m](../../crates/gpu-metal/native/presenter.m), lines 372–391, allocates and uploads `palette` inside `ck_encode_map_pass` on every frame with location pixels. The camera's location list legitimately varies per view; the map input's palette does not. The palette is bounded to 256 RGBA8 entries, so this is **at most 1 KB per frame**, plus the allocation itself.

**Consequence:** The accepted upload cadence is not implemented: ordinary pan/zoom repeatedly recreates invariant map data. No measurable frame-rate loss, leak or lifetime failure was established; this is a small, bounded contract correction.

**Proposed repair draft:** Upload the Metal overlay-palette buffer when admitting its map input, retain it with that resident generation, and bind it for each location pass. Replace and release it under the same completion proof as the generation's other map resources. Preserve allocation-refusal handling and old-generation ownership; leave the view-dependent location buffer separate. Verify unchanged-input reuse, changed-input replacement and the existing visual parity assertions without starting a performance campaign.

**Deduplication:** ck-manager confirmed no accepted deviation, issue or review discussion in answer `4myxini8eetf6bz5f6m8ct4vwn` (2026-11-07), asking that the size and unmeasured cost remain explicit.
