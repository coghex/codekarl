## Findings

### [no-issue] GUIDE-1. Correct the README's obsolete no-third-party-dependencies claim

**Disposition:** documentation drift (minor). **Verification:** verified by pinned source inspection.
**Principle:** `vision.small-libraries`; accepted CK-43 and CK-45 explicitly permit the application dependencies.
**Evidence:** `README.md:194-196` says the application and bridge have no third-party runtime dependencies and that
`cargo tree -e normal` shows only workspace crates. `apps/codekarl/Cargo.toml:16-18` instead declares normal dependencies on
`libc`, `serde` and `toml`. `crates/log/Cargo.toml` has no dependencies; `crates/runtime/Cargo.toml:8-9` depends only on `ck-log`.
This statement remains in the M1 closeout publication and was rechecked in the current source before drafting the proposal.

**Consequence:** a reader gets an incorrect account of the application's dependency/build requirements. The dependencies themselves
are approved and do not violate the vision. No dependency removal or new tooling is warranted.

**Applied replacement** for the three sentences at README lines 194–196:

> The application uses `serde` and `toml` for configuration and `libc` for platform calls. `ck-log` has no third-party dependencies;
> `ck-runtime` depends only on `ck-log`. The CLI spec test uses `serde_json` as a dev-dependency of `apps/codekarl` only.

**Resolved 2026-10-19:** the manager published this replacement as **D1792392362983487000**, retaining the `Cargo.lock` sentence.
The guide verified the accepted README text against the proposal (line wrapping aside) and its receipt/fingerprint. The manager's
verified chat message `xqzttxuer9nmxgzvhk6uayubf2` reports the owner's direct approval: "it looks like i need a quick update to the
readme, make the patch". No issue was needed: the authorized correction was delivered through the ordinary docs lane.

## Known concern, already tracked

CK-47's [owner decision](../../../codekarl-meta/issues/CK-47/comments/1792380502466858000.md) accepts dropped startup/shutdown progress
records but conditions acceptance on capturing errors. Accepted `crates/runtime/src/lib.rs:74-79` sends every lifecycle record through
bounded `log_within`, including errors at lines 215, 240 and 257. `apps/codekarl/src/lifecycle.rs:44` and `:175` do likewise.
`crates/runtime/tests/full_queue_failure.rs:62` expressly expects four drops, including the start failure and terminal failure record.
Thus a healthy sink behind a full queue can still lose the diagnostic. This is an owner-policy gap already represented by CK-52,
not a newly discovered violation of the then-effective CK-47 r7 implementation contract.

[CK-52 r4](../../../codekarl-meta/issues/CK-52/spec/r4.md) was reviewed as a plan, not an implementation. It separates error admission
from the settings lock, reserves capacity, specifies closure arbitration and batch ordering, tracks actual delivery with a contiguous
sequence watermark, and gives pending errors one bounded grace. The test plan includes ordinary-queue errors, overtaking, failure and
panic cases. Its scope includes the runtime assertion that currently expects error loss.
The spec quotes the owner's allowance of a two-second error limit and labels the extra-grace interpretation as the manager's reading.
Finite reserve capacity, contention, failed stdout and a sink too slow for the deadline remain explicit limits; this is not an
unconditional promise that every possible error reaches stdout. No accepted CK-52 implementation is covered here.

## What moved

- **CK-41 + CK-47:** reusable logging, formatting and category filtering; one writer, queue ownership, flush tickets and failure/drop
  accounting. Ordinary admission now waits for space; control-path admission is bounded. Those are distinct contracts, despite the
  older issue titles. Traced writer closure, producer wake-up and sink-panic cleanup.
- **CK-42 + CK-49:** ordered service startup, reverse cleanup of successfully started services, primary/rollback error retention and
  one terminal result. Logging is bounded; the lifecycle API does not itself make arbitrary service execution preemptible.
- **CK-43 + CK-45:** stderr routing at executable entry; explicit, strict TOML configuration; fixed pre-configuration error logging;
  configured lifecycle records; panic/shutdown deadline handling; `_exit(3)` on incomplete flush, avoiding blocked C stdio cleanup.
  Inspected flag-looking filenames, invalid configuration, child process deadlines and stalled/closed-output tests.
- **CK-44 + CK-48:** default-feature tests remain separate from required full Metal validation; disposable toolchain copies carry
  current configuration. Historical runner diffs were read because later CK-50/51 changes are outside this review.
- **Six docs publications:** read exact previous/next diffs for the five runtime-design amendments and final README/tooling closeout.
  The amended loss limits matter to the owner-policy assessment above. Dependency prose in the closeout retains GUIDE-1.
