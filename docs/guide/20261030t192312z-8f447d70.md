## Findings

### [#150] GUIDE-1. Enforce a coherent mapping while a public frame ticket is being built

**Disposition:** owner-approved repair filed as CK-150. **Suggested priority:** P2.
**Verification:** source-verified contradictory public API result; no runtime or GPU reproduction, and no observed demo failure claimed.
**Principle:** `vision.small-libraries`; CK-127 r1’s coherent mapping/table publication and CK-128 r2’s ticket-based slot resolution.

**Evidence at the pin:**

- `crates/gpu-metal/src/ledger.rs:1266` (`begin_frame`) pins the current table version; the resolution cache starts empty.
- `ledger.rs:1126` (`adopt`) can change the active revision while that ticket is Building. The table switch checks only that the spare
  is unpinned and caught up (`crates/gpu-metal/src/bindless.rs:410`), not that resolution against the old ticket has finished.
- `ledger.rs:1915` (`resolve_slot`) reads the key’s current active revision on its first lookup and returns that revision’s native slot.
  It does not check that the returned slot describes that revision in the ticket’s pinned table. Its own API documentation promises
  the slot in that pinned table and one consistent revision per key per frame.
- Consequently: begin a ticket against table A; prepare, commit and adopt a replacement into B; first resolve the key through the old
  ticket. Resolution returns B’s new slot, while `bindless()` still returns A, where that new slot is the checker. If the key was resolved
  before adoption, the cached old revision is now Retired and the repeated lookup instead returns `None`.
- `crates/gpu-metal/tests/textures.rs:2041–2128` deliberately holds a Building ticket across adoption and proves its old table/pixels
  survive, but reads a hard-coded old slot. It never resolves the key again through that ticket. CK-148’s reuse checks end frame 1 before
  adopting between frames; they do not cover this sequence either.

**Impact and boundary:** a direct library client can receive the wrong checker slot or lose a previously resolved image within one frame.
This is a coherence problem, not evidence of a dangling GPU resource: the old table remains pinned and retains its images.
The ordinary presenter is sequential: `presenter.rs:2292` runs its boundary adoption before `scene.rs:986` creates and ends the ticket.
That path avoids the sequence. The public API does not enforce it. CK-148 preserved this behavior rather than introducing it.

**Authority and deduplication:** the current cursor has no open finding; the pinned issues contain the original epoch/mapping obligations
and no follow-up addressing this overlap. Authenticated manager answer `2i5p7h3a9kax8iki4xdhx962ps` (2026-10-30), fully read and claimed,
reports no owner-approved restriction on resolving after adoption and calls this an open library-contract question. It is corroboration,
not repair approval. The relevant source and test files are byte-identical in the current accepted state after CK-149.

**Recommendation:** enforce the presenter’s existing sequencing at the public ledger boundary: keep active-mapping changes pending while
a ticket can still resolve, then permit publication once resolution is closed. Preserve the ability of an already-built packet to finish
against its pinned old epoch. Prefer a bounded sequencing guard over a registry snapshot or per-frame full-map copying; the owner’s
no-performance-regression direction remains a constraint. The exact API/state transition needs normal design/spec review.

**Approved draft filed by ck-manager as CK-150:**

> **Title:** Make public frame-ticket resolution coherent with its pinned bindless epoch.
>
> **Type / priority:** bug, P2. **Basis:** this report’s GUIDE-1 and CK-127/128’s mapping/epoch contract.
>
> A Building ticket can span `adopt`: its table stays old while its first `resolve_slot` reads the new active revision, or a repeated
> lookup loses the retired cached revision. Normal presenter sequencing avoids this, but the safe public ledger API permits it.
>
> Define and enforce when a ticket’s resolution closes relative to active-mapping changes. Recommended behavior: while resolution is
> open, adoption retains committed work pending without switching that ticket’s active mapping. Once resolution is closed, publication
> may proceed and an already-built packet keeps its pinned old table until its explicit ending/completion. Audit the other public
> mapping-mutating entry points against the same rule; none may silently return a slot inconsistent with the ticket’s table.
>
> Add focused regression coverage for (1) first resolution after an attempted overlapping adoption, (2) repeated resolution around it,
> and (3) an already-built old packet surviving a later publication. Check both revision identity and the pixels/slot actually addressed.
> Keep normal presenter order, explicit ticket endings, retirement progress, existing ordinary-path behavior and bounded work. No
> device-idle wait, new per-frame registry copy, broad redesign or new performance gate. The manager schedules any GPU/window validation;
> the existing restriction on Codex-authored crash/panic/fault probes still applies. Use normal independent spec/submission review.
