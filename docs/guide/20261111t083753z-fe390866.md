## Findings

### [#265] GUIDE-1. A destroyed cards/rows selector remains attached to its window

**Disposition:** repair — mismatch to fix, P1. **Verification:** source-verified; no reproduction executed.
**Principle/contract:** `vision.ui-heavy`; CK-259's selector, tab switching and resize behavior; the window attach/detach lifecycle.

**Evidence:** `scripts/ui/lib/location.lua:436` destroys the selector when leaving a card tab or rebuilding the panel. The selector's `destroy` at line 465 destroys its controls and empties `buttons`, but never calls `Window:detach` (`scripts/ui/lib/window.lua:362`). It was attached at `location.lua:470`. A later `window.lua:50` layout still calls its layout method, which dereferences `self.buttons.cards` and `rows` at `location.lua:460`.

**Consequence:** visit Pops or Buildings, switch to Location, then drag the window or select another place: the stale child is laid out with missing buttons. Resizing while a card tab is active is an even shorter path: `location.lua:594` destroys it before `set_outer_size` lays out attached children. The callback raises a Lua error instead of completing the UI action. Existing switching coverage (`apps/codekarl/src/ui_link/location_tests.rs:464`) checks that the selector is gone but does not perform the next layout.

**Repair draft:** detach the selector from its owning window exactly once when destroyed; make repeated destruction harmless. First add a failing windowless witness for Pops/Buildings → Location → drag/title relayout, plus resize while each card tab is active and close/reopen. Assert that dead children are absent, callbacks complete and remaining controls still work. Preserve cards/rows choice and intended scroll behavior.

**Applied disposition:** manager answer `t9yyz2xpyjudgjs2idstreduis` confirmed no earlier issue, deferral or ruling and filed CK-265 from this evidence. Its implementation is outside this pin.

### [#266] GUIDE-2. Ledger refresh changes the rows but keeps their first selection map

**Disposition:** repair — mismatch to fix, P2. **Verification:** source-verified; no reproduction executed.
**Principle/contract:** `vision.player-information`; CK-258's revision refresh and row-to-place navigation.

**Evidence:** `scripts/ui/main.lua:415` builds rows and their `selections` from the current revision. `fill_ledger` at line 459 replaces the visible items in an existing list, but the `on_select` closure created on the first fill still closes over that first `selections` table. Population rows can be added to an earlier place: `crates/economy/src/lib.rs:6082` (`ensure_pop`, called by migration) appends a previously absent pop.

**Consequence:** after such a revision, clicking a row below the insertion can open the wrong place, and the last new rows can do nothing. If the initial Pops list was empty, its later rows have no corresponding selection. The rendered names can be current while their actions are stale.

**Repair draft:** keep the current row-to-place mapping with the current ledger items and replace both on every refresh. Preserve tab choice and the existing scroll policy. Add a windowless test that starts with rows at two places, adds a pop to the earlier place at a new revision, then clicks the inserted, shifted and final rows and checks their place IDs. Also cover initially empty → populated. Do not infer correctness from row text alone.

**Deduplication:** manager answer `6z5ub7xjdkkrn7nzgy326udq6i` confirmed this is neither tracked, deferred nor ruled on and agreed to file it after this report; CK-266 item 1 now carries it. The source function is `ensure_pop`, not the mistaken name in the initial chat question.

### [#266] GUIDE-3. Opening Pops in an existing location window leaves another tab selected

**Disposition:** repair — mismatch to fix, P3. **Verification:** source-verified; no reproduction executed.
**Principle/contract:** `vision.player-information`; CK-258 requires a ledger Pop row to open that place's Pops tab.

**Evidence:** `scripts/ui/lib/location.lua:614` assigns an explicit `tab` to `self.key`. Creation initializes `tabs.new` from that key, but the already-open branch only sets the title, raises the window and renders: it never updates `self.tabs`. `scripts/ui/lib/tabs.lua:145` invokes its selection callback only when the selected key changes.

**Consequence:** with Location or Buildings already selected, a Pops-ledger click renders Pops content while the old tab remains highlighted. Clicking that highlighted old tab cannot restore its content, because the tabs widget believes it is already selected. Another tab must be chosen first. The existing ledger navigation witness (`apps/codekarl/src/ui_link/location_tests.rs:1525`) starts with a fresh panel and misses this path.

**Repair draft:** synchronize the tabs widget and panel content whenever `show` receives an explicit tab, including the already-open branch. Avoid double rendering or callback loops. Add windowless cases starting on Location and Buildings, click a ledger Pop row, assert both selected tab and content are Pops, then click the previously selected tab and verify that it works immediately. Calls without an explicit tab must retain the current selection.

**Deduplication:** manager answer `6z5ub7xjdkkrn7nzgy326udq6i` confirmed no existing issue, deferral or ruling; CK-266 item 2 now carries it.

### [#266] GUIDE-4. The widget viewport stays at 800×600 until the reported size changes

**Disposition:** repair — mismatch to fix, P3. **Verification:** source-verified conditional startup path; the actual first native update was not observed.
**Principle/contract:** `vision.ui-heavy`; CK-257/258 opening geometry and the right-aligned ledger.

**Evidence:** `scripts/ui/lib/window.lua:16` initializes its viewport to 800×600. `scripts/ui/main.lua:28` obtains the opening size from `window.open` and puts it into `view`, but the sole call to `windows.update_viewport` at line 609 is inside the branch for a later differing size. If the first frame reports the same size, the two viewport records remain inconsistent. The widget's position limits at `window.lua:62` and centring use its old viewport.

**Consequence:** at an unchanged 1280×800 UI-unit startup, a 426-unit ledger requests x=854, but the old viewport's maximum x is 768, so the ledger stops 86 units short of the right edge. Default centring and drag limits also use the wrong viewport. A later real size change repairs that state incidentally. The usual fixture first delivers 1800×900, which forces the initialization branch and masks the unchanged-startup case.

**Repair draft:** initialize the widget library viewport from the `window.open` result before creating windows. Add a windowless startup witness whose first frame has exactly the opened size, without a resize; assert the ledger's right edge, default centring and drag limits, then verify a subsequent resize. Test the opening UI-unit result rather than hard-coding native point dimensions.

**Deduplication/limit:** manager answer `yaeuxi4szxgynvvb58yeegqnn2` agrees by source; CK-266 item 3 now carries it. The owner previously reported the opening UI looked right; that is not contradicted by an unexecuted claim about the first native frame. The worker's no-resize witness should establish the affected path. Initialization should not depend on an incidental size-change notification.

### [#266] GUIDE-5. Card scrolling loses small deltas by feeding snapped placement back into input

**Disposition:** repair — mismatch to fix, P3. **Verification:** source-verified arithmetic; no probe executed.
**Principle/contract:** `vision.ui-heavy`; CK-259 clause 3: a point scroll is its amount in units.

**Evidence:** `scripts/ui/lib/cards.lua:217` starts each event from `scroll_offset`; `set_pos` at line 224 clamps and snaps it, retaining only the snapped value. `scripts/ui/lib/ui.lua:13` rounds half up on the two-unit UI-pixel grid. Unlike this stack, `scripts/ui/lib/list.lua:427` retains a raw `pos` and snaps its displayed position separately.

**Consequence:** away from the boundaries, repeated point-scroll amount +1 at displayed offset 26 computes `snap(25)=26` forever, while amount −1 computes `snap(27)=28` and moves two units per event. Slow scrolling can stick in one direction and run at twice the requested rate in the other. Whole-line tests do not expose it.

**Repair draft:** retain a clamped unsnapped position and derive snapped placement from it; clamp the raw position consistently when items or heights change. Add windowless repeated +1 and −1 point-event cases showing that two events move one UI pixel in either direction, plus fractional accumulation, line steps and shrink/boundary behavior. Keep rendering and hit geometry on the pixel grid.

**Deduplication:** manager answer `we3625hbm5bmwzqjx2pn4dcnmi` confirmed no issue, deferral or ruling and agreed this is a P3 mismatch; CK-266 item 4 now carries it in a separate patch.
