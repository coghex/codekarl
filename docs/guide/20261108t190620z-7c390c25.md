## Findings

### [#222] GUIDE-1. Decide whether the diagnostic checker must remain untinted

**Disposition:** filed as CK-222. **Severity:** P3.

**Owner decision (2026-11-08):** "Fix: always white", relayed in authenticated manager message `j9uy53f7ugmfhv7hu3v56scyna`. This reverses the earlier manager ruling. CK-222 r1 requires identity tint on every checker fallback, both backends and binding modes; resolved textures retain their tint. The issue is open, not accepted.

**Verification:** verified by source, without a rendering run. **Principle/contract:** `vision.modding`, CK-215 effective r2 §2.3: the checker at slot 0 draws untinted.

**Evidence:** at this pin, [Metal batch.rs](../../crates/gpu-metal/src/batch.rs), lines 397–404, and [Vulkan batch.rs](../../crates/gpu-vulkan/src/batch.rs), lines 344–346, pass `instance.tint` when a scene texture has no resolved revision. Their instance shaders pass that tint to the fragment; [quad.metal](../../crates/gpu-metal/shaders/quad.metal), lines 120–130, and [scene_bindless.frag](../../crates/gpu-vulkan/shaders/scene_bindless.frag) multiply the checker sample too. The ordinary fragment paths also multiply it. With zero-alpha tint, the premultiplied sample is zero; dark tint can make the checker hard to distinguish.

**Consequence:** a pending or failed scene texture can lose its diagnostic checker entirely, rather than merely change colour. This is reachable through the public tint API and matters for diagnosing themed or modded UI. It does not imply a resource-lifetime or game-state failure.

**Deduplication and authority:** ck-reviewer-2 already raised the tinted checker as CK-215 review N1 in `.pipeline/coordination/runtime-m55/ck215-submission-review-1-reviewer-2.md`. The manager accepted it as cosmetic under approval `14bf7acd`, without a spec amendment. Authenticated manager reply `j2xwj5gnu4zm95wbhqubhjdxhe` confirms this was a **manager ruling, not owner approval**, and asks that the stronger transparency consequence be put to the owner. This is a reconsideration with that provenance, not a claim that the review missed N1.

**Proposed action:** restore opaque white tint for the missing-texture fallback in both backends/modes; preserve the requested tint once the texture resolves. Add CPU batch assertions for transparent and dark scene tints with unresolved keys, and extend the existing checker/readback coverage when runs are authorized. Keep batching, compatibility quads and map drawing unchanged. Alternatively, if the owner deliberately wants the checker to inherit tint (including intentional invisibility), amend the contract explicitly and record that disposition. Transparent hidden widget quads make this a real policy choice; do not silently reverse the ruling.

### [#223] GUIDE-2. Duplicate button icon names orphan scene quads

**Disposition:** filed as CK-223. **Severity:** P3. **Verification:** verified by source, without a probe.

**Owner decision (2026-11-08):** "Fix it", relayed in authenticated manager message `j9uy53f7ugmfhv7hu3v56scyna`. CK-223 r1 requires duplicate rejection before any frame, quad or region is created, with windowless invalid-input and destruction coverage. The issue is open, not accepted.

**Principle/contract:** `vision.modding` and widget resource ownership; CK-217 §3 accepts a nonempty array of known, equal-width icon names, creates its icons up front and switches them by tint. Button destruction must remove its quads.

**Evidence:** [button.lua](../../scripts/ui/lib/button.lua), lines 85–111, validates icon names, widths and array shape but does not reject duplicates. Lines 180–196 create one quad for every occurrence and store it as `self.icon_quads[name]`, replacing the previous ownership entry. Lines 265–278 switch only the retained entries; lines 286–303 destroy only those entries.

**Consequence:** `button.new{icons = {"pause", "pause", "play"}, ...}` creates two initially visible pause quads but retains only the second handle. `set_icon("play")` leaves the first pause drawn; moving the button leaves it behind, and `destroy()` cannot remove it. In the base group it survives until scene teardown, retaining a scene slot and texture reference. Group destruction can eventually reclaim it, but ordinary button destruction cannot. The shipped time bar uses unique names and does not trigger this case.

**Deduplication:** authenticated manager reply `e7vw3eice4zaktw9u7un7qpzia` confirms no issue or ruling covers it.

**Proposed repair draft:** reject a repeated name in `checked_icons`, with a named Lua error, before any frame or icon quad is created. Extend the existing windowless widget test with duplicate-name refusal and zero scene allocation, and verify that a valid multi-icon button's destruction removes every created quad. Preserve the existing tint-only/no-op switching behavior. Scope is `scripts/ui/lib/button.lua` and its owning application widget tests; no engine change or window run is needed to establish this regression.
